## Trigger and evidence

- Trigger: user-confirmed material implementation blocker in slice 02.01, recorded in [02-01-pi-integration.md](../implementation/02-01-pi-integration.md) "Attempt 1" and "Interruption 1 - formal refinement selected". User selection (verbatim): "lets move to grill with docs to refine and find a solution for this, or a compromise".
- Fact: under tmux, Pi 1.4.0 enables only button-motion mouse tracking. `@earendil-works/pi-tui/dist/tui-alt-screen.js` L184-L193 writes `?1000h ?1002h ?1004h ?1006h` (no `?1003h`) when `TMUX`, `ZELLIJ`, or `STY` is set or `TERM` starts with `tmux` or `screen`, with the source comment "Multiplexers can lag when every pointer movement is forwarded". No setting or environment override exists in that path (verified by the orchestrator).
- Fact: tmux reports the Pi pane `mouse_all_flag=0 mouse_button_flag=1 mouse_sgr_flag=1`; the user's real hover produced no move event; only a click woke the widget (user visual check 1, item d failed).

## Objective

Replace hover-to-wake under tmux with a behavior the extension can deliver without toggling mouse modes, and adjust the run-time policy and acceptance that assumed hover, keeping performance first and KISS.

## Affected contract

- RQ05 (never toggle mouse modes) conflicts with RQ06 ("Hover or click makes a widget live") and AC06 ("hover thaws to a new frame within about 50 ms") under tmux.
- RQ06 / D17 unfocused rule ("freezes 10 s after the last pointer activity over it") assumed hover moves; under tmux pointer activity exists only as press, drag, release, and wheel.
- PD06 (one live widget; another widget becoming live freezes the previous one) is unaffected in substance; only the trigger changes.
- Tool and hint text ("hover or click to interact") and the e2e hover step (synthetic SGR 35, which a real tmux client never sends).

## Affected completed work

- Fact: 01.01 (page layer, freeze and thaw) and 01.02 (kitty transport, harness, AC01/AC02) do not depend on hover delivery; retained as completed (`22eed8a`, `8f8396c`).
- Fact: 02.01 Attempt 1 is preserved uncommitted and frozen pending To Spec reconciliation. Its checks pass (typecheck, 94 unit, 23 browser, 8 e2e x3) and user visual items a, b, c, e passed. Its hover branch (`move` events in `src/component.ts`) remains valid where the terminal reports motion (plain Ghostty).

## Confirmed facts and evidence

- Fact: a press on a frozen widget already wakes it and then delivers the same press to the page, because widget operations are serialized (`src/component.ts` `press` calls `manager.pointer` then `w.mouse`; `src/manager.ts` `pointer` queues `makeLive` through `w.run`). Thaw measured at about 6-30 ms (01.01), so the waking click is not lost.
- Fact: a press focuses the widget (RQ05); keys then go to the widget until Escape, Ctrl+C, or a click elsewhere in Pi releases it (`src/manager.ts` release path).
- Fact: in plain Ghostty without tmux, Pi enables `?1003h`, so hover moves should arrive there (source only, not run; manual check scheduled in 02.02 AC14).
- Fact: Ghostty's own mouse reporting and tmux forwarding offer no way for an extension to learn pointer position without a mode request; tmux forwards motion to a pane only when the pane requested it.
- Fact: consequently, under tmux the page receives `mouseMoved` only during drags, so CSS `:hover` styles and hover-triggered tooltips inside a widget do not track the pointer there.
- Fact: the preserved 02.01 code already freezes a widget on release (`src/manager.ts` release path) and runs a new widget live with the 10 s idle timer from creation.
