# Terminal graphics under tmux

Load this page when changing widget or `show_image` rendering (placeholder grid, kitty uploads, scaling, recovery), widget mouse input, or the tmux-driven e2e, perf, and manual-check tooling.

## Placeholders and passthrough

- **Never put a placeholder cell in the pane's last column** - under tmux 3.6b a Unicode placeholder written into the last column loses its row and column diacritics (tmux attaches them to the previous cell), so Ghostty cannot place it and every image row except the first shows a blank right edge. `maxGridCols(width)` in `src/component.ts` keeps the grid at `width - 1`; e2e grid-hit tests did not detect this, only a user visual check did. ([02.02 evidence](../spec/archive/261028-1700-interactive-html-widgets-for-pi/implementation/02-02-lifecycle-acceptance.md))
- **Image data sent while the pane's window is hidden is dropped** - tmux forwards kitty passthrough only for visible panes, so a widget drawn while the user is in another window stays blank until a re-send (a click on an unfocused widget, a resize, or `/widgets-refresh`); the extension does not detect window switches. Run e2e, perf, and visual checks in a visible pane of the attached client's current window. ([verification](../spec/archive/261028-1700-interactive-html-widgets-for-pi/verification.md))
- **Pi 1.4.0 enables only button-motion mouse tracking under tmux, Zellij, or screen** - hover never reaches the extension there, so do not build or test hover-dependent behavior under tmux and never toggle mouse modes to obtain it (RQ05, PD09). ([R001](../spec/archive/261028-1700-interactive-html-widgets-for-pi/refinements/R001.md))
- **Never upload a new frame to the image id the placeholder rows show** - Ghostty 1.4.0 deletes an image and its placements as soon as a new transmission to the same id begins (`loadAndAddImage` in its `src/terminal/kitty/graphics_exec.zig`), so the rows stay blank until the last chunk arrives; large frames (about 1 MB, hundreds of 4 KB chunks) flash badly, small ones (about 27 KB) rarely visibly. `KittyImage` in `src/kitty.ts` uploads each new frame to the spare of two ids and the rows switch to it; only scaled and recovery re-sends reuse the shown id, so rows already written (regular-mode scrollback) stay valid. Check flashing with a large, detailed fixture: a small rotating square did not reproduce it. ([verification](../spec/archive/261029-1840-widget-input-fixes-and-rendering-polish/verification.md))

## Image payloads

- **Send every image as a PNG with `t=d`; the terminal cannot take URLs or JPEG** - the kitty graphics protocol has no URL transmission medium, and Ghostty 1.4.0 accepts only PNG (`f=100`) or raw RGB/RGBA payloads, not JPEG, WebP, GIF, or SVG. Pi 1.4.0 also disables its own image output whenever `TMUX` is set (`pi-tui/dist/terminal-image.js` returns `images: null`). `show_image` therefore fetches in Node and sends PNG like widget frames: PNG stays in Node (`src/png.ts`), other formats are rasterized by the session's headless browser in a short-lived page that has no network access and does not count toward `MAX_PAGES` (`src/image.ts`). ([show-image plan](../spec/archive/261029-2034-show-image-tool/plan.md))

## Pi mouse input

- **In fullscreen, Pi consumes every mouse sequence before extension input handlers run** - pi-tui's `TuiAltScreen` registers its viewport listener first and returns `consume` for every wheel and SGR mouse sequence, so `ctx.ui.onTerminalInput` never sees mouse input (a probe saw 0 of 6 sequences). Raw mouse handling goes through `RawInputHook` in `src/rawinput.ts`, which keeps one listener at the front of pi-tui's private `inputListeners` Set behind a feature check and re-applies it after renderer changes; without the field the hook is skipped and click-outside release is unavailable. ([plan Decision log](../spec/archive/261029-1840-widget-input-fixes-and-rendering-polish/plan.md))
- **pi-tui reports trackpad sideways scrolling as presses** - its `parseWheelEvent` accepts only vertical wheel directions, so SGR codes 66 and 67 (macOS trackpads send them during ordinary scrolling) reach components as a `press` with button `right` or `none`. Never treat those presses as clicks: the raw input hook consumes them, and without the hook `WidgetComponent` ignores them on unfocused widgets. ([plan](../spec/archive/261029-1840-widget-input-fixes-and-rendering-polish/plan.md))

## Test tooling

- **Capture panes without trimming leading lines** - trimming `tmux capture-pane -p` output drops blank top rows and shifts every row index by one; use `tmuxLines()` from `scripts/perf/lib.ts` when computing click coordinates. Coarse grid-hit tests still pass with a one-row shift, so check the component-relative `y` when adding precise click tests. With `-e`, tmux emits a color only where it changes, so placeholder rows after the first may carry no color code (`locate` in `tests/e2e/lib.ts` handles this). A widget's grid alternates between two image ids; `locate` matches either through the dev log's `spareId`, so pass the persisted `imageId`. `locate` sees only the visible pane: content added after a widget (for example `show_image` rows or tool output) can scroll its grid out of view, so draw or open the widget a test must click last (the perf disk phase opens a second widget after its `show_image` calls). ([02.02 evidence](../spec/archive/261028-1700-interactive-html-widgets-for-pi/implementation/02-02-lifecycle-acceptance.md), [show-image verification](../spec/archive/261029-2034-show-image-tool/verification.md))
- **Run the full e2e suite and user visual checks in a dedicated tmux window you create** - the harness (`openSplit` in `scripts/perf/lib.ts`) splits the pane named by `TMUX_PANE` only when it is in the attached client's current window, the pre-existing suites need an 80x24 split, and the user's pane layout may be too narrow or change between question and answer; do not lower the harness size requirements or resize the user's panes. Create a window with only a long-lived placeholder pane (`tmux new-window -d -n <name> 'sleep 7200'`; short `sleep N` panes expire), ask the user to switch to it, confirm `#{window_active}` and the client's `#{window_id}` (and for visual checks the pane width, pinned with `tmux resize-pane -x`, and visibility from the dev log) before running `TMUX_PANE=<new pane> npm run test:e2e` or relying on an answer, then kill only that window. Re-check the client's current window immediately before every harness run, because the user may leave it during long sessions; if it is not the dedicated window, stop and ask, since `openSplit` otherwise silently splits the user's current pane. ([02.02 evidence](../spec/archive/261028-1700-interactive-html-widgets-for-pi/implementation/02-02-lifecycle-acceptance.md), [verification](../spec/archive/261029-1116-widget-usage-guidance-and-check-widget/verification.md), [1840 verification](../spec/archive/261029-1840-widget-input-fixes-and-rendering-polish/verification.md))
